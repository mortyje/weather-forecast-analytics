# Модель данных Core DWH

## 1. Назначение

Core DWH — интегрированный слой хранилища погодных данных, предназначенный для хранения истории прогнозов и фактических метеорологических наблюдений.

Модель строится в третьей нормальной форме (3НФ). Аналитические витрины формируются на основе Core с использованием dimensional modeling (схемы «звезда»).

Основные задачи Core:

- Сохранение истории полученных прогнозов без перезаписи предыдущих снимков.
- Хранение детальных почасовых прогнозных значений.
- Хранение фактических метеорологических наблюдений и их исправлений.
- Обеспечение связности, целостности и прослеживаемости данных.
- Подготовка интегрированных данных для аналитических витрин.

Документ описывает целевую модель. Реализация таблиц и dbt-моделей будет выполнена отдельно.

## 2. Архитектура DWH

Хранилище включает четыре логических слоя.

| Слой | Назначение |
|---|---|
| Raw / Landing | Исходные сообщения источников и метаданные Kafka |
| Staging | Извлечение JSON, типизация, стандартизация и первичные проверки |
| Core / DDS | Нормализованные сущности, связи и исторические данные |
| Data Marts | Факты и измерения для аналитики и визуализации |

### Raw

Данные сохраняются максимально близко к исходному виду.

Уже реализована таблица `raw.forecast_events`, содержащая сообщения Kafka, их ключи, offsets и временные метки.

В дальнейшем будет добавлено хранение исходных событий с фактическими наблюдениями.

### Staging

Staging реализуется средствами dbt. Основные операции:

- Извлечение полей из JSON.
- Приведение значений к корректным типам.
- Преобразование временных меток к UTC.
- Разворачивание почасовых массивов.
- Проверка обязательных полей и допустимых значений.
- Подготовка данных для загрузки Core.

Простые staging-модели преимущественно материализуются как SQL views. Более сложные промежуточные преобразования выделяются в отдельные dbt-модели.

Отдельный ODS не предусматривается.

### Core / DDS

Данные структурируются по принципам 3НФ. Справочные сущности, снимки прогнозов, почасовые значения и наблюдения хранятся раздельно.

### Data Marts

Используется dimensional modeling: фактовые таблицы и согласованные измерения.

Витрины предназначены для расчёта MAE, RMSE, Bias, анализа горизонтов прогнозирования и построения дашбордов.

## 3. Логическая модель Core

Для Core предусмотрено семь таблиц:

- `core.locations`
- `core.weather_sources`
- `core.weather_stations`
- `core.location_station_assignments`
- `core.forecast_snapshots`
- `core.forecast_hours`
- `core.weather_observations`

### 3.1. core.locations

Справочник городов и конфигурационных точек прогнозирования.

**Зерно:** одна строка на одну локацию.

| Поле | Тип | Описание |
|---|---|---|
| location_id | TEXT | PK, внутренний идентификатор |
| name | TEXT | Название локации |
| latitude | NUMERIC(9,6) | Текущая широта |
| longitude | NUMERIC(9,6) | Текущая долгота |
| timezone | TEXT | Часовой пояс IANA |

`location_id` соответствует идентификатору из конфигурации Python Ingestion, например `moscow`.

Исторические координаты отдельных запросов дополнительно сохраняются в `forecast_snapshots`.

### 3.2. core.weather_sources

Справочник источников погодных данных.

**Зерно:** одна строка на одного поставщика.

| Поле | Тип | Описание |
|---|---|---|
| source_id | TEXT | PK |
| name | TEXT | Название поставщика |

Предусмотрены источники `open_meteo` и `meteostat`.

### 3.3. core.weather_stations

Справочник метеорологических станций.

**Зерно:** одна строка на одну станцию конкретного поставщика.

| Поле | Тип | Описание |
|---|---|---|
| station_id | TEXT | PK, внутренний идентификатор |
| source_id | TEXT | FK → weather_sources |
| external_station_id | TEXT | Идентификатор у поставщика |
| name | TEXT | Название станции |
| latitude | NUMERIC(9,6) | Широта |
| longitude | NUMERIC(9,6) | Долгота |
| elevation_m | DOUBLE PRECISION | Высота над уровнем моря |

Ограничение уникальности: `(source_id, external_station_id)`.

### 3.4. core.location_station_assignments

История назначения метеостанций локациям.

**Зерно:** одно назначение станции локации на определённый период.

| Поле | Тип | Описание |
|---|---|---|
| location_id | TEXT | FK → locations |
| station_id | TEXT | FK → weather_stations |
| valid_from | TIMESTAMPTZ | Начало действия |
| valid_to | TIMESTAMPTZ | Конец действия или NULL |

Предварительный PK: `(location_id, valid_from)`.

Для одной локации интервалы назначений не должны пересекаться. В MVP предполагается одна основная станция на заданный период.

История назначений сохраняется, чтобы изменение выбранной станции не приводило к потере контекста исторических сравнений.

### 3.5. core.forecast_snapshots

История получения прогнозов.

**Зерно:** один снимок прогноза, сформированный одним успешным запросом к источнику.

| Поле | Тип | Описание |
|---|---|---|
| snapshot_id | TEXT | PK |
| location_id | TEXT | FK → locations |
| source_id | TEXT | FK → weather_sources |
| requested_at | TIMESTAMPTZ | Начало запроса |
| collected_at | TIMESTAMPTZ | Получение ответа |
| requested_latitude | NUMERIC(9,6) | Запрошенная широта |
| requested_longitude | NUMERIC(9,6) | Запрошенная долгота |
| response_latitude | NUMERIC(9,6) | Широта из ответа |
| response_longitude | NUMERIC(9,6) | Долгота из ответа |
| raw_topic | TEXT | Топик Kafka |
| raw_partition | INTEGER | Партиция Kafka |
| raw_offset | BIGINT | Offset сообщения |

Ограничение уникальности: `(raw_topic, raw_partition, raw_offset)`.
