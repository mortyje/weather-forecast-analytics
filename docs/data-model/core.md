# Модель данных Core DWH

## 1. Назначение

Core DWH — интегрированный слой хранилища погодных данных, предназначенный для хранения истории прогнозов и актуальных версий метеорологических наблюдений.

Модель строится в третьей нормальной форме (3НФ). Аналитические витрины формируются на основе Core с использованием dimensional modeling (схемы «звезда»).

Основные задачи Core:

- Сохранение истории полученных прогнозов без перезаписи предыдущих снимков.
- Хранение детальных почасовых прогнозных значений.
- Хранение актуальных версий фактических метеорологических наблюдений.
- Обеспечение связности, целостности и прослеживаемости данных.
- Подготовка интегрированных данных для аналитических витрин.

Документ описывает таблицы Core и правила хранения данных.

## 2. Архитектура DWH

Хранилище включает четыре логических слоя.

| Слой | Назначение |
|---|---|
| Raw / Landing | Исходные сообщения источников и метаданные Kafka |
| Staging | Извлечение JSON, типизация, стандартизация и первичные проверки |
| Core / DDS | Нормализованные сущности, связи и исторические данные |
| Data Marts | Факты и измерения для аналитики и визуализации |

### Raw

Данные сохраняются максимально близко к исходному виду.

Таблицы `raw.forecast_events` и `raw.observation_events` содержат исходные сообщения Kafka, их ключи, offsets и временные метки.

### Staging

Staging реализуется средствами dbt. Основные операции:

- Извлечение полей из JSON.
- Приведение значений к корректным типам.
- Преобразование временных меток к UTC.
- Разворачивание почасовых массивов.
- Проверка обязательных полей и допустимых значений.
- Подготовка данных для загрузки Core.

Простые staging-модели преимущественно материализуются как SQL views. Более сложные промежуточные преобразования выделяются в отдельные dbt-модели.

Отдельный ODS не предусматривается.

### Core / DDS

Данные структурируются по принципам 3НФ. Справочные сущности, снимки прогнозов, почасовые значения и наблюдения хранятся раздельно.

### Data Marts

Используется dimensional modeling: фактовые таблицы и согласованные измерения.

Витрины предназначены для расчёта MAE, RMSE, Bias, анализа горизонтов прогнозирования и построения дашбордов.

## 3. Логическая модель Core

Для Core предусмотрено семь таблиц:

- `core.locations`
- `core.weather_sources`
- `core.weather_stations`
- `core.location_station_assignments`
- `core.forecast_snapshots`
- `core.forecast_hours`
- `core.weather_observations`

### 3.1. core.locations

Справочник городов и конфигурационных точек прогнозирования.

**Зерно:** одна строка на одну локацию.

| Поле | Тип | Описание |
|---|---|---|
| location_id | TEXT | PK, внутренний идентификатор |
| name | TEXT | Название локации |
| latitude | NUMERIC(9,6) | Текущая широта |
| longitude | NUMERIC(9,6) | Текущая долгота |
| timezone | TEXT | Часовой пояс IANA |

`location_id` соответствует идентификатору из конфигурации Python Ingestion, например `moscow`.

Исторические координаты отдельных запросов дополнительно сохраняются в `forecast_snapshots`.

### 3.2. core.weather_sources

Справочник источников погодных данных.

**Зерно:** одна строка на одного поставщика.

| Поле | Тип | Описание |
|---|---|---|
| source_id | TEXT | PK |
| name | TEXT | Название поставщика |

Предусмотрены источники `open_meteo` и `meteostat`.

### 3.3. core.weather_stations

Справочник метеорологических станций. Одна строка соответствует одной станции поставщика.

| Поле | Тип | Описание |
|---|---|---|
| station_key | TEXT | Технический ключ `MD5(CONCAT(source_id, ':', station_id))` |
| source_id | TEXT | Идентификатор поставщика, ссылка на `weather_sources` |
| station_id | TEXT | Идентификатор станции у поставщика |
| name | TEXT | Название станции |
| latitude | NUMERIC(9,6) | Широта станции |
| longitude | NUMERIC(9,6) | Долгота станции |
| last_seen_at | TIMESTAMPTZ | Время последнего сбора наблюдений для станции |

При выборе атрибутов сначала учитываются события с обеими координатами, затем время сбора. Старые события Meteostat версии 1 позволяют завести станцию с координатами `NULL`. События версии 2 заполняют эти поля.

### 3.4. core.location_station_assignments

История назначений метеостанций локациям. Одна строка соответствует назначению станции локации с определённого момента.

| Поле | Тип | Описание |
|---|---|---|
| assignment_id | TEXT | Технический ключ, вычисленный из `location_id`, `station_key` и `valid_from` |
| location_id | TEXT | Идентификатор локации, ссылка на `locations` |
| station_key | TEXT | Технический ключ станции, ссылка на `weather_stations` |
| valid_from | TIMESTAMPTZ | Начало действия назначения из события наблюдений |
| valid_to | TIMESTAMPTZ | Начало следующего назначения, верхняя граница не включается. `NULL` для последнего известного назначения |
| first_seen_at | TIMESTAMPTZ | Самое раннее время сбора события с этим назначением |
| last_seen_at | TIMESTAMPTZ | Самое позднее время сбора события с этим назначением |

Повторные сборы с той же станцией и тем же временем назначения объединяются в одну строку. История строится по событиям наблюдений. Назначение попадёт в неё, когда сборщик опубликует хотя бы одно событие с его метаданными. При сборе с перекрытием отдельные измерения могут относиться к часам до `valid_from`.

### 3.5. core.forecast_snapshots

История получения прогнозов.

**Зерно:** один снимок прогноза, сформированный одним успешным запросом к источнику.

| Поле | Тип | Описание |
|---|---|---|
| snapshot_id | TEXT | PK |
| location_id | TEXT | FK → locations |
| source_id | TEXT | FK → weather_sources |
| requested_at | TIMESTAMPTZ | Начало запроса |
| collected_at | TIMESTAMPTZ | Получение ответа |
| requested_latitude | NUMERIC(9,6) | Запрошенная широта |
| requested_longitude | NUMERIC(9,6) | Запрошенная долгота |
| response_latitude | NUMERIC(9,6) | Широта из ответа |
| response_longitude | NUMERIC(9,6) | Долгота из ответа |
| raw_topic | TEXT | Топик Kafka |
| raw_partition | INTEGER | Партиция Kafka |
| raw_offset | BIGINT | Offset сообщения |

Ограничение уникальности: `(raw_topic, raw_partition, raw_offset)`.

`snapshot_id` формируется детерминированно из идентификатора исходного события. Повторная обработка одного Kafka-сообщения даёт тот же идентификатор.

### 3.6. core.weather_observations

Актуальные почасовые измерения. Бизнес-ключ состоит из `station_key` и `observed_at`.

| Поле | Тип | Описание |
|---|---|---|
| station_key | TEXT | Технический ключ станции, ссылка на `weather_stations` |
| observed_at | TIMESTAMPTZ | Время измерения в UTC |
| temperature_c | NUMERIC | Температура воздуха, °C |
| humidity_pct | NUMERIC | Относительная влажность, % |
| precipitation_mm | NUMERIC | Осадки, мм |
| wind_speed_kmh | NUMERIC | Скорость ветра, км/ч |
| source_event_id | TEXT | Идентификатор исходного Kafka-события |
| source_collected_at | TIMESTAMPTZ | Время сбора версии измерения |
| source_ingested_at | TIMESTAMPTZ | Время загрузки события в Raw |

Core хранит последнюю полученную версию измерения для каждой станции и часа. Версия выбирается по времени сбора, затем по времени загрузки и идентификатору события. История всех поступивших версий остаётся в `raw.observation_events` и доступна в почасовом представлении Intermediate. Отсутствующие погодные показатели хранятся как `NULL`.
